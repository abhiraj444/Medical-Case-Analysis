## 1. High-Level Architecture

This application is a full-stack web app built on modern technologies, designed for medical professionals to get AI-powered insights.

-   **Frontend**: **Next.js** (using the App Router) and **React** provide a fast, server-rendered user interface.
-   **UI Components**: **ShadCN UI** and **Tailwind CSS** are used for a modern, responsive design system.
-   **Backend & Data**: **Firebase** provides a suite of services for authentication, database (Firestore), and file storage.
-   **AI**: **Genkit** is used as the framework to define, manage, and execute all interactions with the underlying Generative AI models (Google's Gemini).

The application is designed to be serverless, with the Next.js frontend communicating directly with Firebase services and Genkit AI flows, which run as server-side functions.

## 2. Project Structure

The codebase is organized into the following key directories:

```
.
├── src
│   ├── app/                # Next.js pages/routes (e.g., '/', '/login')

│   ├── hooks/              # Custom React hooks (e.g., useAuth, useToast)
│   ├── lib/                # Utility functions and library initializations (Firebase, etc.)
│   └── types/              # TypeScript type definitions for the app
├── public/                 # Static assets (images, etc.)
└── package.json            # Project dependencies and scripts
```

## 3. Frontend (Next.js & React)

### Pages & Routing

The app uses the Next.js App Router. Each folder inside `src/app` corresponds to a URL route.

-   `src/app/page.tsx`: The main "AI Diagnosis" page.
-   `src/app/content-generator/page.tsx`: The "Content Generator" page for creating presentations.
-   `src/app/history/page.tsx`: Displays a list of the user's saved cases.
-   `src/app/login/page.tsx`: The user authentication page.
-   `src/app/layout.tsx`: The root layout for the entire application, containing the main HTML structure, header, and context providers.

### Key Components

-   **`Header.tsx`**: The main navigation bar, showing links and user account information.
-   **`DiagnosisCard.tsx`**: A card component to display a single provisional diagnosis from the AI.
-   **`QuestionDisplay.tsx`**: A component that shows the user's summarized question and any uploaded images.
-   **`SlideEditor.tsx`**: A powerful component that allows users to view, edit, and export the JSON-based slide presentation generated by the AI. It handles the logic for exporting to PDF and Word.
-   **`HistoryCard.tsx`**: A card used on the `/history` page to show a summary of a previously saved case.

### State Management

The application primarily uses React's built-in hooks for state management (`useState`, `useEffect`, `useContext`).

-   **Local State**: `useState` is used for managing component-level state, such as form inputs, loading indicators, and AI results.
-   **Global State (Auth)**: `useContext` combined with `AuthContext.tsx` provides the current user's authentication status across the entire application, avoiding the need to pass props down through many levels.

### Styling

-   **ShadCN UI**: Provides the foundational, unstyled UI components (`Button`, `Card`, `Input`, etc.).
-   **Tailwind CSS**: Used for all styling. Utility classes are applied directly in the JSX for rapid development.
-   **`globals.css`**: Defines the application's theme (colors, fonts, etc.) using CSS variables, allowing for easy theming and dark mode support.

## 4. Backend Services (Firebase)

Firebase is used for all backend functionality. The configuration is handled in `src/lib/firebase.ts`.

### Authentication

-   **Service**: Firebase Authentication.
-   **Implementation**: `src/context/AuthContext.tsx` wraps the application and uses Firebase's `onAuthStateChanged` listener to track the user's login state. `src/app/login/page.tsx` handles the sign-in and sign-up logic using email/password and Google Sign-In.

### Database (Firestore)

-   **Service**: Firestore (a NoSQL document database).
-   **Data Model**: All user work is saved in a top-level collection named `cases`. Each document in this collection represents a single "case" and has a `type` field to distinguish between workflows.

    -   **`DiagnosisCase` (`type: 'diagnosis'`)**: Stores the input patient data and the output from the `aiDiagnosis` flow.
    -   **`ContentCase` (`type: 'content-generator'`)**: Stores the input topic/question and the resulting AI answer and generated slide presentation.

-   **Interaction**: The app uses the Firebase SDK to create, read, and update these case documents. When a user views a case from their history, the `caseId` is passed in the URL, and the app fetches the corresponding document from Firestore.

### File Storage

-   **Service**: Firebase Storage.
-   **Workflow**: To avoid exceeding Firestore's 1MB document size limit, file uploads are handled as follows:
    1.  User selects or pastes a file (image or PDF).
    2.  The file is uploaded to a user-specific folder in Firebase Storage with a unique filename (using the `uuid` library).
    3.  The file's content (as a data URI) is sent to the Genkit AI for analysis.
    4.  The public **download URL** (a short string) returned by Firebase Storage is saved in the Firestore case document, **not** the large file itself.

## 5. AI Logic (Genkit)

Genkit is the framework that orchestrates all calls to the Gemini Large Language Model (LLM). All AI logic is located in the `src/ai/flows/` directory.

### Core Concepts

-   **Flow**: A flow (`ai.defineFlow`) is a server-side function that encapsulates a specific AI task. It defines the expected input and output data structures.
-   **Prompt**: A prompt (`ai.definePrompt`) contains the instructions for the LLM. It uses Handlebars templating (`{{{...}}}`) to insert dynamic data from the flow's input.
-   **Schema**: Zod schemas (`z.object({...})`) are used to define the exact shape of the input and output data for each flow. This ensures type safety and instructs the LLM to return data in a specific JSON format.

### AI Flows Explained

-   **`ai-diagnosis.ts`**:
    -   **Purpose**: To provide a differential diagnosis based on patient data.
    -   **Input**: `patientData` (string) and/or `supportingDocuments` (array of data URIs).
    -   **Output**: A JSON array of diagnosis objects, each containing the diagnosis, confidence level, reasoning, and missing information.

-   **`answer-clinical-question.ts`**:
    -   **Purpose**: To provide a direct, detailed answer to a clinical question.
    -   **Input**: `question` (string) and/or `images`.
    -   **Output**: A JSON object containing the `answer`, `reasoning`, and a `topic` for the question.

-   **`summarize-question.ts`**:
    -   **Purpose**: To take raw user input (text and images) and clean it up for display. It's instructed to ignore irrelevant UI elements in screenshots.
    -   **Input**: `question` and/or `images`.
    -   **Output**: A JSON object with a single `summary` field containing the cleaned-up text.

-   **`generate-slide-outline.ts`**:
    -   **Purpose**: To create a structured presentation outline on a given topic.
    -   **Input**: A `topic`, desired `numberOfSlides`, and optional context from a clinical question.
    -   **Output**: A JSON array of slide objects. Each slide has a `title` and a `content` array, which can contain structured items like paragraphs, lists, and tables.

-   **`modify-slides.ts`**:
    -   **Purpose**: To edit an existing slide deck based on user commands.
    -   **Input**: The current array of `slides`, the `selectedIndices` to modify, and an `action` (e.g., 'expand_content').
    -   **Output**: The complete, new array of all slides.

## 6. Core Application Workflows

### Workflow 1: AI Diagnosis

1.  **Input**: User enters patient data and/or uploads supporting documents on the main page (`/`).
2.  **Submission**: The `handleSubmit` function is triggered.
    -   Files are uploaded to Firebase Storage.
    -   Three AI flows are called in parallel: `aiDiagnosis`, `answerClinicalQuestion`, and `summarizeQuestion`.
3.  **State Update**: The React state is updated with the results from the AI calls, causing the UI to re-render and display the `QuestionDisplay`, `DiagnosisCard`s, and the direct clinical answer.
4.  **Persistence**: A new "case" document is created in Firestore, saving the user's input (with file URLs) and the complete AI output. The new `caseId` is stored in the state.

### Workflow 2: Content Generation

1.  **Input**: User navigates to `/content-generator` and enters either a clinical question or a general topic.
2.  **Submission**: The appropriate `handle...Submit` function is called.
    -   If it's a question, `answerClinicalQuestion` and `summarizeQuestion` are called.
    -   A "case" is created or updated in Firestore to save this initial step.
3.  **Presentation Generation**: The user selects a presentation length and clicks "Generate Presentation."
    -   The `generateSlideOutline` flow is called with the topic and context from the previous step.
    -   The returned JSON slide data is saved to state and updated in the Firestore case document.
4.  **Editing & Export**: The `SlideEditor` component is displayed, allowing the user to review the generated slides.
    -   The user can export the presentation to PDF or Word. The export functions in `SlideEditor.tsx` read the slide data from the component's state and use libraries (`jspdf`, `docx`) to create the downloadable file.
    -   The user can also use the AI to modify the slides, which calls the `modifySlides` flow.
